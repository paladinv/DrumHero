# Optional Song Library accounts, sync, and sharing

The local Song Library works without an account. The optional account panel uses Supabase Auth and Postgres with row level security. No secret/service-role key is used in the browser.

## Connect a project

1. Create or choose a Supabase project and enable email/password authentication. Keep email confirmation enabled.
2. Apply `supabase/migrations/202610190001_song_libraries.sql`, `supabase/migrations/202610190002_song_library_history.sql`, `supabase/migrations/202610210001_practice_snapshots.sql`, `supabase/migrations/202610210002_teacher_rosters.sql`, `supabase/migrations/202610210003_scoped_song_shares.sql`, `supabase/migrations/202610220001_song_builder_presence.sql`, `supabase/migrations/202610220002_shared_song_review_comments.sql`, `supabase/migrations/202610220003_song_builder_collaboration_broadcast.sql`, `supabase/migrations/202610250001_shared_song_comment_threads.sql`, and `supabase/migrations/202611190002_song_public_catalog.sql` through the Supabase SQL editor or your normal migration workflow.
3. Add the variables from `.env.example` to `.env.local` and set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` from the project's API settings. Use the public publishable key, never a service-role or secret key.
4. Restart the app (and rebuild when deploying). Open Song Library → Backup and account sync → Connect account.
5. Create/confirm an account and sign in. Create a cloud library from this device or review an existing library before applying it locally.

For account-backed classrooms, also apply `supabase/migrations/202611170005_classroom_groups.sql`. The Progress → Learners and assignments panel then offers shared classroom creation and joining. Review [the classroom data policy](CLASSROOM_DATA_POLICY.md) before production use. This migration is separate from Song Library sync; it does not upload progress history or recordings.

This repository supplies the integration and migration. It does not provision or configure a hosted Supabase project automatically.

## Song Builder collaboration

Song Builder publishes short-lived presence and note-edit broadcasts for a reviewed cloud library. Members see each other’s current section, pattern, and selected note. Owners and editors receive full song updates in real time; viewers can observe but cannot publish edits. Apply both `202610220001_song_builder_presence.sql` and `202610220003_song_builder_collaboration_broadcast.sql` and enable Realtime private channels in Supabase. Presence stops when a tab closes or loses its connection. The broadcast is a live working copy; use normal cloud sync to persist it to the shared library, where concurrent revisions may still require conflict review.

## Behavior

- Connecting a library uploads shared song arrangements and library organization plus the active learner's notes, queues, goals, schedules, custom learning paths, rubric assessments, rehearsal run outcomes, and practice progress. Collections, kit profiles, and setlists remain shared library data. Song Library learner history and notes are tagged to the profile ID, so export **learner sync identity** in the shared-device tools and import it on another device before syncing that learner there. Recording audio, reference audio, and their metadata remain on the current device. Use the encrypted Song Library backup (up to 96 MiB of audio) or the full-device local backup to transfer audio.
- Changes save locally first. Once enabled, sync runs while the Song Library page remains open (including when the account drawer is closed), debounces local edits and sends them with the last reviewed revision. Use **Sync now** to request an immediate upload of the current device library. The panel reports when edits are waiting, synced, paused, or offline. Local edits made offline remain available after refresh. Reopening the library page asks you to review the cloud library before resuming uploads. Changes made in other tools are included in that review.
- Concurrent updates are rejected atomically by the database. Review conflicting song fields and arrangement sections before merging, or explicitly choose the entire cloud/device version. Mixed resolution preserves both sides’ additions and uses the chosen version for changed fields and sections. Same-ID collection, queue, setlist, learning path, and custom groove conflicts can keep the device copy, cloud copy, or both as separate records. A merge retains planning records with matching IDs and combines distinct records. Song deletions should be represented by archiving, which syncs normally.
- Cancel, pause, sign out, or changing libraries stops future uploads. An already submitted request can finish; its revision will be detected on the next review.
- Owners can grant viewer/editor access to an existing confirmed account by email and revoke it. Viewers can read a cloud library but cannot update it. Editors can update its contents but cannot grant permissions. Database checks enforce access even if a client is modified.
- The selected-song share panel creates a separate viewer-only snapshot from individually selected songs and an optional collection. It strips song, section, part, and kit private notes, journals, annotations, progress, plans, recordings, and reference audio. The recipient must have an existing confirmed account; the owner can grant or revoke viewer access. Recipients can copy selected arrangements into their local library. Scoped snapshots are separated from the regular sync list, and the database rejects editor access and editor writes to them. Owners can update a snapshot as a new revision. A recipient who downloaded a copy can review public metadata, kit setup, and arrangement changes, then apply selected updates; their local notes, practice history, and recordings stay on the device.
- Permission revocation blocks subsequent database access. It cannot remove a copy someone previously downloaded to their device.
- Members of a selected-song snapshot can add comments anchored to a song, section, part, and optional bar, then reply in a thread. They can also post structured hit-add/remove proposals with a part-grid step and rationale. Owners and editors see the current-versus-proposed hit diff and can apply a current-revision proposal to a local shared copy after confirmation; originals and the shared snapshot remain unchanged. A stale proposal must be refreshed before it can be applied. Owners and editors can resolve or reopen a thread; authors and snapshot owners can delete comments. Comments record the snapshot revision they refer to and are separate from private notes and practice data. Existing installations must apply `202610220002_shared_song_review_comments.sql` and `202610250001_shared_song_comment_threads.sql` for threaded comments and resolution.
- Revision history retains the previous 20 cloud versions, including the device label supplied by the editor. Owners/editors can review a historical version and recover it as a new revision; viewers can inspect history. Device labels are user-supplied, not verified device identities.
- The account panel shows pending edits and cloud revisions. When a connection fails, local data remains available; review the cloud snapshot before retrying.

MIDI exchange accepts Standard MIDI format 0 or 1 percussion tracks on channel 10. Imports use the initial tempo and meter, clamp tempo to Drum Hero’s 40–200 BPM range with the source value shown, quantize to sixteenth notes, read at most 20,000 hits per track, and cap the arrangement at 128 bars; skipped events are reported for review. Exports map supported voices to General MIDI drum notes, preserve arrangement tempo and meter changes, and can include the full song or one section up to 4,096 bars. Custom voices without a General MIDI mapping are omitted.

The native iOS Song Library imports and exports single-song `drum-hero-song-v1` files and multi-song `drum-hero-song-library-pack-v1` files. Import opens a review for duplicates, replacement, copies, and skipped songs; mixed packs can still import supported songs when other entries use unsupported iOS drum voices. Imported iOS projects are stored locally in SwiftData and are not included in progress backup or account sync. iOS practice currently supports kick, snare, hi-hat, tom, and crash. The web arrangement review lists unsupported voices and their affected parts before export, and the iOS import review names songs and voices it cannot read. Use the web Kit compatibility tool to create a supported variation while retaining the full web arrangement.

Song Library usability observations can be recorded in the local drummer review form. The form captures the test surface, input setup, and drummer experience; it saves anonymous notes only after the drummer agrees. Reviews remain in this browser and are excluded from sync and backups until someone explicitly exports the review JSON file. Exports use format v3; existing local v2 observations remain readable. Reference playback speed is saved with local library metadata; audio stays local. These records help structure human testing but do not replace player, educator, or physical-device review.

## Verify a configured project

Use separate owner, editor, and viewer accounts. Verify that the editor can save but cannot grant access; the viewer cannot save through the API; an unrelated account cannot list/read a library; and revoking access blocks subsequent API calls. Open two editors at the same revision and confirm the second write produces a conflict. Disconnect the network, edit locally, reload, reconnect, and review/merge before resuming sync. Also verify signup email delivery in the configured project.

The Progress page also has separate, opt-in sync for the active learner's lesson completion, Practice Pad scores, Trainer rounds, input calibration, and Rhythm ear-training history, review schedules, and challenge packs. It uses the same Supabase account but stores a private per-learner snapshot with revision checks and up to 20 recoverable versions. Review cloud data before choosing cloud, device, or merged data. To sync a named learner across browsers, export **learner sync identity** in the shared-device tools on Progress and import it on the other device; this small file carries only the profile ID and display name. Teacher assignments can separately sync as a private account roster with revision checks and 20 prior versions; review the cloud roster before explicitly loading it, which replaces the local assignment list. Rhythm ear-training teacher reports remain local and are exchanged only as explicit report files. An audio clip imported for rhythm transcription is analyzed in the browser; only the saved notation pattern may enter the learner's challenge pack and optional private progress snapshot, while the source audio stays local. Recording audio, reference audio, and their metadata stay local and are excluded from Song Library sync and sharing. Delete a cloud practice snapshot from the Progress page; deletion removes its revision history while local data remains.

For a teacher who should not receive the learner's account credentials, the shared-device tools also support a learner/guardian-approved progress report file. It contains the learner's name and profile ID, completed lesson IDs, and up to 100 recent standard scored practice summaries (pattern, source, tempo, accuracy, and date), with no hit-level timing, settings, audio, or recordings. Export requires an explicit permission checkbox. Import the learner sync identity first so the report matches the correct local profile. Importing reports combines distinct practice records, updates the classroom overview, and can satisfy matching assignments. Remove reports per learner from the classroom overview; this also reopens assignments completed only from the removed report, while local or manually recorded completion remains. Reports and their evidence IDs are excluded from teacher roster uploads and stay on the receiving device unless separately exported. This is an explicit file transfer, separate from private account sync and teacher roster sync.

The repository's unit/browser checks cover local workflows, change signatures, and conflict selection. Live Auth, email delivery, database policies, and device-specific audio behavior require a configured Supabase project and physical devices.

For the isolated browser conflict check, build with test-only public values, then run the mocked service flow:

```sh
NEXT_PUBLIC_SUPABASE_URL=https://drum-library-test.supabase.co NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=test-publishable-key npm run build
PLAYWRIGHT_CLOUD_MOCK=1 npx playwright test tests/e2e/song-cloud.spec.ts
npm run build
```

The test intercepts that endpoint locally. It verifies pending offline edits, revision conflicts, explicit merge review, retrying the reviewed revision, and excluding recording metadata from uploads. The last build restores the installation's normal configuration. Do not deploy the mock-account build.

## Revision history migration

Existing installations must apply `202610190002_song_library_history.sql` after the initial migration. Each successful revision update keeps its previous state, timestamp, and editor-supplied device label. The database retains the previous 20 revisions per library. Opening history never restores automatically: review a revision, then apply it to create a new cloud revision using the latest expected revision. A concurrent write still produces a conflict. Viewers can read history but cannot save recovered data to the shared library.

## Offline interface

The production build generates `public/song-offline-assets.json`. The explicit offline download stores the main learning and practice page shells, static code, fonts, app manifest, built-in drum sounds, and 3D kit models in a service-worker cache. The Offline panel compares the saved asset version with the current build, estimates site storage, and flags low remaining quota. Song, recording, and learner data continue using localStorage/IndexedDB. The worker never caches account, database, or permission requests. Offline internal links reload the cached page shell so they do not depend on an online Server Component request. A failed update removes its incomplete cache while keeping the last completed download available. Removing the offline download does not remove songs or recordings. Refresh the download after a deployment; browsers may evict cached resources, so export backups for important material.

The WebKit offline browser check stops an isolated local origin rather than using Playwright's broken offline emulation for service-worker navigations ([upstream issue](https://github.com/microsoft/playwright/issues/42775)). Chromium also passed a direct offline-emulation refresh check during development.


## iOS Song Library account exchange

The native Song Library can explicitly exchange compatible personal songs with an existing editable web account library. Use the same Drum Hero account as Progress sync; iOS reuses its Keychain session. In the Song Library menu choose **Sync with web library**, select an owner/editor library, and review before each transfer. Import adds only songs missing by ID and title/artist. Upload is append-only, keeps web-only fields on existing songs intact, and requires an explicit action. It skips voices the current iOS project model cannot play. Recordings and reference audio remain local. Account updates use the web library's revision compare-and-swap; when a concurrent edit is detected, iOS reloads the latest revision and asks you to review again before retrying.

This exchange requires the same iOS Supabase URL and publishable key described above plus the existing song-library migrations. Create the account library on web first, then grant the iOS account editor access. Viewer-only and scoped snapshot libraries do not appear as upload destinations. The project remains local unless you choose an import or upload action.

## Public repertoire catalog

Apply `supabase/migrations/202611190002_song_public_catalog.sql` to enable public browsing and moderated submissions. Published entries are readable without an account; submissions require sign-in, the song's current rights checklist, a license description, and a separate public-distribution attestation. The submission payload omits private annotations, rehearsal comments, rights-review internals, and retained original MusicXML. Only assigned reviewers can publish or return a submission, and authors cannot review their own work. Provision reviewers through a trusted Supabase admin session with `insert into public.drum_song_catalog_reviewers(user_id) values ('AUTH_USER_UUID') on conflict do nothing;`, replacing the placeholder with the reviewer’s confirmed account UUID; the app has no self-assignment path. The catalog stores user-provided rights statements and moderation status, not an independent verification of copyright ownership.

Calendar reminders can be exported from the selected song's Overview as an `.ics` file. Events are 30 minutes long, include a 15-minute calendar alarm, and serialize saved times in UTC; delivery depends on the calendar app that imports the file.

MusicXML imports retain the original source file locally up to 256 KiB. The local original can be exported after a current rights review; cloud libraries and public submissions omit it. Automatic reference-audio tempo maps and per-hit hand/foot assignments are suggestions and annotations, respectively, and should be reviewed by the drummer before use.
